## 1. Executive Summary

Build a fully local CCTV crowd-intelligence application for a two-floor mess hall. The application must ingest several video sources, use the actual RTX 5070 Ti Laptop GPU for hardware-accelerated perception, calculate explainable crowd metrics, and present the results in a professional operations dashboard.

The first accepted demonstration processes four simultaneous feeds and proves:

- Real person detection and camera-local tracking.
- Directional entry/exit counting, zone occupancy, and floor occupancy.
- A building occupancy estimate with explicit count-conservation diagnostics.
- Duplicate suppression for a controlled pair of overlapping cameras.
- Independent Floor 1 and Floor 2 maps connected by explicit staircase transitions.
- A controlled cross-floor handover, with ambiguous associations remaining `UNKNOWN`.
- Queue measurement, explainable congestion, and camera-health monitoring.
- Real hardware telemetry and recorded benchmarks from this laptop.
- Cold-start operation with outbound Internet disabled.

The architecture must remain useful when migrated to an RTX A6000. Scaling should change deployment settings, models/engines, stream configuration, and measured capacity rather than require a rewrite of the analytics, dashboard, event contracts, or facility model.

### 1.1 Implementation mandate

The engineer implementing this PRD is responsible for software, computer vision, DeepStream integration, backend, frontend, systems integration, benchmarking, and deployment automation.

Implementation must proceed incrementally from real hardware verification to an operational application. Scaffolding, pseudocode, a playing video, successful container startup, GPU utilization alone, or an empty-metadata pipeline does not satisfy the deliverable.

Inspect the existing directory before making changes and preserve useful work. At preparation of this document, the project directory contained no existing application files.

### 1.2 Requirement language

- **MUST / REQUIRED:** Acceptance-blocking requirement.
- **SHOULD:** Preferred implementation; deviations require a documented engineering reason.
- **MAY / OPTIONAL:** Outside the critical path unless explicitly promoted into scope.
- **Measured:** Produced by a recorded run on the stated hardware and configuration.
- **Configured target:** An engineering setting or acceptance threshold, not an observed result.
- **Unknown / unavailable:** A first-class value with a reason, never a substitute zero.

## 2. Product Goals, Users, and Scope

### 2.1 Goals

1. Convert multiple CCTV views into useful facility-level crowd intelligence.
2. Demonstrate trustworthy counting despite overlapping views and camera reconnects.
3. Explain uncertainty, incomplete coverage, stale feeds, and unresolved handovers.
4. Keep all runtime inference, footage, derived data, and user interaction local.
5. Measure actual performance on the confirmed 12 GB-class RTX 5070 Ti laptop.
6. Establish a maintainable path toward a measured twenty-camera A6000 deployment.

### 2.2 Primary users

| User | Need | Success condition |
| --- | --- | --- |
| Facility operator | Understand occupancy, queues, congestion, and camera status | Can identify the affected floor, zone, camera, and evidence quickly |
| Demo presenter | Show a coherent person-to-facility analytics sequence | Can replay a documented scenario with real inference and explain uncertainty |
| CV engineer | Evaluate detection, tracking, calibration, and association | Can rerun fixed clips and compare task-specific metrics |
| System maintainer | Install, operate, diagnose, and migrate the application | Can use documented scripts and inspect local logs, versions, and benchmarks |

### 2.3 Required user stories

- As an operator, I can see four live/replayed feeds with current person boxes, local track IDs, counts, and health.
- As an operator, I can distinguish camera-visible counts from deduplicated zone/floor occupancy and estimated building occupancy.
- As an operator, I can view Floor 1 and Floor 2 independently and inspect directional stair traffic.
- As an operator, I can inspect an alert, understand its deterministic trigger, and open local supporting evidence.
- As an operator, I can see when a count is stale, inferred, uncertain, or affected by missing coverage.
- As an engineer, I can replace a file source with an RTSP URL through configuration without changing analytics code.
- As an engineer, I can reproduce a detector comparison and identify the exact model, engine, calibration, and configuration used.
- As a presenter, I can start the application after a reboot with outbound Internet disabled.

### 2.4 Initial scope

| Area | Required for the accepted laptop demo |
| --- | --- |
| Sources | Four simultaneous file feeds; common source abstraction supports RTSP |
| Detection | TensorRT person detection; benchmark both selected candidates |
| Tracking | One authoritative NVIDIA tracker per camera |
| Counting | Directional IN/OUT, ROI counts, occupancy, reconciliation |
| Multi-camera | One calibrated overlap pair; one controlled staircase/gap transition |
| Analytics | At least one validated queue and one congestion rule |
| Facility | Two separate floor coordinate systems and an explicit portal graph |
| Operations | Camera health, alerts, history, evidence, real system telemetry |
| UI/API | Local React dashboard and FastAPI backend or justified equivalent |
| Persistence | Local SQLite behind a PostgreSQL-ready persistence interface |
| Validation | Replay harness, measured capacity report, offline acceptance evidence |

### 2.5 Prohibited capabilities

The application MUST NOT implement:

- Facial recognition, facial enrollment, or permanent biometric profiles.
- Demographic inference, emotion recognition, or persistent gait biometrics.
- Permanent real-world person identities.

Temporary global IDs represent session/visit-scoped tracking hypotheses. Appearance similarity must never be presented as proof of identity.

### 2.6 Deferred features

The following are excluded from the critical path:

- Full NVIDIA VSS infrastructure, elaborate local vector-search infrastructure, or a production-scale gallery.
- Large VLMs, complex action recognition, or large-scale training.
- A twenty-camera production-capacity claim or a twenty-camera-first UI.

## 3. Non-Negotiable Constraints and Fixed Architecture Decisions

### 3.1 Fully local runtime

The following MUST remain local:

- Source footage, decoded frames, crops, embeddings, and tracking identifiers.
- Events, logs, analytics, database files, evidence clips, and model files.
- Inference, association, dashboard assets, charts, maps, fonts, and API traffic.

Runtime MUST NOT depend on:

- Cloud inference, OpenAI APIs, external VLM APIs, or remote CCTV analytics.
- Cloud databases, hosted vector databases, or hosted TypeSafe AI Jev calls.
- Uploading footage, crops, embeddings, event data, or logs.
- A CDN, Internet model lookup, external font server, or external WebRTC discovery service.

One-time dependency/model downloads during installation are acceptable. Disable dependency telemetry and automatic model/update checks where relevant. The application must fail clearly on a missing local artifact rather than silently download it during offline operation.

### 3.2 Selected architecture

```text
NVIDIA DeepStream 9.2
  + GStreamer
  + NVDEC hardware decode
  + GPU preprocessing
  + TensorRT detection
  + NVIDIA multi-object tracking
  + deterministic crowd analytics
  + calibrated floor/camera topology
  + constrained optional appearance association
  + local API, persistence, and dashboard
```

DeepStream 9.2, MV3DT, and NVIDIA VSS Warehouse multi-camera/Re-ID workflows are the selected reference direction. The complete VSS stack is not a first-demo dependency.

Do not repeat broad repository, model, or market research. A focused compatibility investigation is permitted when a selected dependency is actually unavailable, unsupported in the intended environment, or incompatible. Record the failing version, command, error, resolution, and implications.

### 3.3 Preferred software interfaces

- Prefer current supported DeepStream Service Maker / `pyservicemaker` interfaces.
- Use C++ for performance-sensitive or unsupported bindings where appropriate.
- Avoid basing new integration on deprecated `pyds` examples.
- Prefer existing reliable NVIDIA components over unnecessary rewrites.
- Pin release-matched components rather than mixing unrelated tutorial versions.

### 3.4 Resource-priority order

When the 12 GB-class GPU is under pressure, preserve workloads in this order:

1. Reliable ingestion.
2. Timestamps and camera health.
3. Person detection.
4. Local tracking.
5. Entry/exit counting.
6. Occupancy.
7. Overlap deduplication.
8. Floor topology.
9. Cross-camera handovers.
10. Queue/congestion analytics.
11. Dashboard enhancements.
12. Optional advanced AI.

Disable optional Re-ID/VLM work, reduce optional preview cost, and shed nonessential work before degrading authoritative tracking/counting. Every automatic degradation must be visible in health/telemetry.

## 5. Demonstration Footage and Facility Fixture

### 5.1 Four-feed starting layout

Use four representative, authorized clips. A suitable configuration is:

| Camera | Example role | Example floor |
| --- | --- | --- |
| `cam_01` | Entrance/exit; visible Floor 1 stair-access portal where available | Floor 1 |
| `cam_02` | Dining/crowd area and a queue region | Floor 1 |
| `cam_03` | Calibrated overlapping view of part of Camera 2 coverage | Floor 1 |
| `cam_04` | Floor 2 staircase landing, queue, or transition view | Floor 2 |

These are fixture roles, not assertions about camera placement or available footage. Adapt coverage through configuration. The controlled stair handover needs a real visible origin portal and destination portal; the overlap demonstration needs genuinely overlapping, time-aligned footage.

### 5.2 Fixture requirements

- Record source provenance, permission, checksum, codec/profile, resolution, FPS, and duration.
- Include standing, seated, distant, occluded, dense-group, tray-carrying, entrance, queue, and staircase examples where available.
- Include a known positive clip with clearly visible people for the detector smoke test.
- Include hard-negative frames with tables/chairs and background structures.
- Include a short manual reference set for counting, crossings, queue membership, and association.
- Store synchronization offsets and their uncertainty for related file feeds.
- Keep evaluation footage/reference labels stable across comparisons.

Unrelated clips cannot prove cross-camera identity continuity or physical overlap. If suitable data is missing, obtain an authorized controlled recording or mark that gate blocked. Do not invent a successful handover from unrelated videos.

### 5.3 Replay behavior

- Support deterministic start offsets, synchronized start groups, seek/restart, and real-time pacing.
- Treat file PTS as media time and map it to an explicit replay-session timeline.
- Label wall-clock replay time separately from original capture time.
- Increment the camera epoch on a loop/restart that resets tracker continuity.
- Partition/reset demo counters intentionally between replay runs; replayed events must not silently inflate a prior run.
- Keep max-throughput replay distinct from real-time operation in benchmark reports.

## 6. System Architecture

### 6.1 Logical data flow

```text
File / RTSP source
  -> source manager and compressed-stream branch
  -> bounded per-camera queues + timestamp/health metadata
  -> NVDEC
  -> GPU preprocessing and batching
  -> TensorRT detector
  -> one authoritative tracker per camera
  -> camera-local deterministic analytics
  -> calibrated projection and overlap fusion
  -> topology-constrained transition association
  -> occupancy / queue / flow / congestion / reconciliation
  -> local versioned events and latest-state snapshots
  -> FastAPI + local persistence
  -> React dashboard, history, alerts, evidence

System telemetry -> local metrics collector -> API/dashboard + benchmark reports
Compressed source branch -> bounded local recorder -> event evidence extraction
```

### 6.2 Deployment units

| Unit | Responsibility | Failure boundary |
| --- | --- | --- |
| Perception worker | Decode, detection, tracker metadata, calibration projection | Restartable; camera epochs invalidate prior local continuity |
| Analytics service/module | Counts, fusion, association, queues, congestion, health | Versioned state; replayable events |
| Backend | Configuration read/validation, APIs, persistence, history, alert state | Must expose readiness and dependency health |
| Frontend | Camera grid, two-floor maps, KPIs, alerts, telemetry | Reconnects to snapshots/updates without changing authoritative state |
| Recorder/evidence worker | Compressed recording buffers, event clips, retention | Optional recording failure is surfaced independently |
| Telemetry collector | Real machine/process/per-camera measurements | Unsupported measurements are explicitly unavailable |
| Optional appearance worker | Selective embeddings and constrained candidate scores | Failure cannot stop authoritative detection/tracking/counting |

These are logical boundaries. Backend and analytics may initially share a process where that reduces complexity. Avoid introducing Kafka, Milvus, etcd, MinIO, or a distributed broker solely for this demo.

### 6.3 Internal transport

- Use a bounded local metadata channel between perception and analytics/backend.
- Prefer local Unix sockets or local HTTP/WebSocket IPC according to supported SDK integration.
- Keep frame buffers out of ordinary JSON event messages; use local references/preview channels.
- Use versioned event envelopes, sequence numbers, idempotency keys, and explicit overflow behavior.
- Maintain separate latest-state updates and durable discrete events. High-rate track samples may be coalesced; crossing/association/alert events must not be silently discarded.
- On a transport gap, flag degraded state and resynchronize from a snapshot. Do not silently claim complete history.

### 6.4 GPU memory and backpressure

- Keep decoded surfaces and preprocessing GPU-resident where supported.
- Avoid unnecessary GPU-to-CPU-to-GPU copies.
- Use bounded per-source queues, bounded event queues, and a bounded preview queue.
- Use per-source deadlines so a delayed/offline stream cannot indefinitely block a batch.
- Size batch capacity and tracker targets from actual workload and measured memory.
- Prefer dropping old display/processing frames to accumulating an unbounded real-time backlog.
- Record where/why a frame was dropped: source, decode, scheduling, analytics, transport, or preview.
- Treat intentional detector sampling separately from unexpected frame loss.
- Make recording independent of analytics sampling where practical.

### 6.5 Source abstraction

Analytics must consume a common observation contract, independent of source type. Switching a camera from `file` to `rtsp` must require configuration changes and normal validation, not changes to occupancy/queue/fusion code.

File and RTSP ingestion must support invalid paths/URLs, unsupported codecs, corrupt input, end-of-stream, reconnect, and source timeout without taking down other cameras where the runtime permits isolation.

## 7. Perception Requirements

### 7.1 Hardware decode

- Use NVDEC through the release-supported GStreamer/DeepStream path.
- Verify the actual selected decoder and supported input codec/profile.
- Record decode FPS, errors, dropped frames, and decode utilization where exposed.
- Inspect negotiated caps/surface memory and eliminate accidental software-decode fallback.
- Do not use NVENC session counts as decode-capacity evidence.

### 7.2 Detector candidates and selection

Benchmark these candidates on the actual RTX 5070 Ti using the same fixture set:

1. `PekingU/rtdetr_v2_r18vd`.
2. `Roboflow/rf-detr-small`.

Pin exact checkpoint revisions and artifacts. Export/preprocessing/parser code must match the selected model. Record class mapping, input shape, resize/letterbox policy, normalization, box coordinate convention, and output interpretation.

Select the baseline using:

- Site-specific person precision/recall, misses, and false positives.
- Seated/distant/occluded-person behavior and dense-scene saturation.
- Downstream tracking stability and count quality.
- p50/p95 latency, throughput, and VRAM on this laptop.
- Export, TensorRT, and DeepStream integration reliability.

Published benchmark scores alone cannot determine the winner. Both candidates require a real attempt; an unavailable/incompatible candidate needs concrete failure evidence and a documented decision rather than an invented comparison row.

Prefer TensorRT and FP16 where supported without unacceptable accuracy loss. Consider INT8 only after a measured calibration/evaluation run. Keep the detector adapter replaceable.

### 7.3 Blackwell and strongly typed RT-DETR

The current DeepStream MV3DT RT-DETR reference requires:

```ini
strongly-typed=1
```

This is mandatory for the applicable RT-DETR configuration on this Blackwell laptop. Use the actual release-supported configuration/build mechanism, and include the setting in engine provenance.

Strong typing and precision selection must follow the installed TensorRT version. Do not assume an old FP16 builder flag can be combined with a strongly typed network; use supported graph typing/casts and record the actual precision behavior.

Required positive-path validation:

- Expected person detections greater than zero on known positive frames.
- Valid nonzero-area bounding boxes in the correct coordinate system.
- Metadata reaching the application, not merely an internal model tensor.
- Tracker IDs after tracking is enabled.
- Actual crossings/occupancy events after analytics is enabled.

A live video window, running container, nonzero GPU utilization, or exit code zero is insufficient. Add a known-clip smoke/integration test that fails when expected metadata is absent.

### 7.4 Detection and tracker capacity audit

Audit and record all applicable limits:

- Detector top-k and maximum output queries/detections.
- Parser output capacity and class filtering.
- NMS thresholds/capacity where the selected model/parser uses NMS.
- `maxTargetsPerStream` and tracker allocation limits.
- Shadow-track limits and lost-track retention.
- Metadata pool limits and transport batch limits.
- Appearance embedding batch limits and crop queues.

Do not inherit `topk=20` or similar tutorial caps. Set limits with measured peak person count plus documented headroom, accounting for VRAM. Emit a saturation warning when an output reaches a known cap; dense-scene evaluation must explicitly check saturation.

### 7.5 Local tracking

Start with NvDCF / NvMultiObjectTracker. NvSORT, ByteTrack, and BoT-SORT may be comparison baselines, but only one tracker may generate authoritative production IDs for a feed at a time.

Every local track key is:

```text
(camera_id, camera_epoch, local_track_id)
```

Example:

```text
cam_02 / epoch_3 / track_17
```

Requirements:

- Allocate a new camera epoch when reconnect/restart/loop invalidates tracker continuity.
- Preserve epoch uniqueness across process restarts, using durable generation state or a unique session token.
- Never reinterpret a reused numeric ID in a new epoch as the previous physical person.
- Expose tentative, confirmed, temporarily lost, and ended lifecycle states using the chosen tracker adapter.
- Preserve raw tracker IDs; global association is a separate layer.
- Do not count a shadow/predicted track as a fresh visual detection.
- End or degrade track-derived analytics after configured freshness limits.

## 8. Time, Synchronization, and Camera Health

### 8.1 Timestamp contract

Preserve distinct fields for:

| Time concept | Meaning |
| --- | --- |
| RTP timestamp | Source media-clock tick value, when available |
| PTS | Presentation time with an explicit time base |
| Receive time | Host receipt time, with UTC and monotonic timing for local durations |
| Capture-time estimate | Best available source/capture time, nullable |
| Clock quality | Provenance and synchronization-quality category |
| Timestamp uncertainty | Estimated uncertainty, nullable with reason |
| Clock offset/drift | Estimated source-to-reference offset and drift, when measurable |

Host arrival time must not be relabeled as capture time. Use monotonic clocks for local elapsed-time calculations so a wall-clock adjustment does not corrupt dwell/crossing timers.

For future RTSP deployment:

- Use local NTP where supported.
- Inspect RTCP Sender Reports to relate RTP media clocks to sender time.
- Use PTP only when actual camera/network hardware supports it.
- Detect discontinuities, out-of-order timing, drift, and clock resets.
- Disable or widen/reject cross-camera matching according to synchronization quality.

Report true capture-to-result age only when capture timing is defensible. Otherwise report receive-to-result processing age and media/replay lag separately, with clear labels.

### 8.2 Camera-health detection

Implement from the first multi-source integration:

- Disconnection and reconnect attempts.
- Stale frame/metadata age.
- Frozen or repeated-frame sequences.
- Black frames and decode errors.
- Source/decode/analytics FPS drops.
- Latency/queue-depth growth.
- Timestamp anomalies.
- Possible camera movement, crop/zoom change, and calibration invalidation.

Repeated-frame detection should combine image/scene evidence with timestamp behavior and persistence. A stationary scene alone must not automatically be classified as a frozen feed.

### 8.3 Health model

Support operator-visible states:

```text
HEALTHY
DEGRADED
OFFLINE
CALIBRATION WARNING
```

Internally, keep connectivity/processing health and calibration validity separately so both problems can be displayed at once. Include reason codes, state-change timestamps, retry count, last-good-frame age, and affected analytics.

Health thresholds, debounce, recovery windows, and reconnect backoff must be configurable. A bad camera should degrade its own analytics/coverage confidence rather than make all cameras appear healthy with old values.

### 8.4 Stale-data semantics

- Show stale counts with their observation time and quality flag.
- Do not convert missing observations to zero occupancy.
- Do not retain a last-seen person forever as currently visible.
- Suspend calibration-dependent metrics when geometry is invalid.
- Prevent stale tracks from creating new line crossings or handovers.
- Reflect missing boundary coverage in building-occupancy quality.

## 9. Two-Floor Facility Model and Calibration

### 9.1 Separate coordinate systems

Create independent `floor_1` and `floor_2` coordinate systems. A position is meaningful only with its floor ID and calibration revision. Do not flatten both floors into one plane.

Each floor supports:

- Dimensions, units, origin, axis convention, and a local floor-plan asset.
- Dining regions, queue regions, corridors, entrances, and exits.
- Staircase entrances, landings, and explicit transition portals.
- Pillars, walls, blind areas, camera coverage polygons, and overlap regions.
- Zone ownership rules for authoritative counting.

### 9.2 Topology graph

Represent legal transitions as directed or bidirectional edges with allowed direction and plausible travel-time bounds.

```text
Dining_F1_A
  -> Stair_F1_Entrance
  -> Stair_A
  -> Stair_F2_Landing
  -> Dining_F2_A
```

No unrestricted all-camera matching is allowed. The topology must exclude unreachable cameras, impossible floor jumps, paths through walls, and simultaneous observations that violate physical feasibility.

### 9.3 Calibration capabilities

Use current NVIDIA MV3DT/calibration tooling where useful. Support:

- Intrinsics and lens-distortion assumptions.
- Extrinsics and ground-plane mapping.
- Manual surveyed anchors and world projection.
- Projection uncertainty and validation error.
- Source resolution, crop, and zoom metadata.

Manual calibration is acceptable. Accuracy and traceability matter more than automatic calibration.

For ground-plane crowd mapping, use an appropriate person footpoint, usually the bottom-center of the box with visibility/occlusion caveats. Seated or occluded people may have poor ground contact estimates; flag uncertainty rather than assert a precise world position.

### 9.4 Calibration lifecycle

Every calibration record includes:

```text
revision_id
camera_id
created_at
source_resolution
crop_and_zoom_assumptions
distortion_assumptions
intrinsics/extrinsics or homography
surveyed_anchor_references
validation_method
validation_error and units
status
```

Invalidate or mark suspect after camera movement, zoom, crop, or resolution changes. Keep revision history and store the applied revision on generated observations/events.

When calibration is missing, retain camera-local detection/tracking where possible. World density, calibrated overlap fusion, and other geometry-dependent metrics must be unavailable/degraded instead of fabricated.

## 10. Multi-Camera Association and Duplicate Suppression

### 10.1 Distinct problem types

Implement overlapping-view fusion separately from non-overlapping gap/stair association. They have different evidence, timing, and failure modes.

### 10.2 Controlled overlapping-camera fusion

Start with one calibrated overlapping pair using MV3DT or equivalent calibrated multi-view logic.

Required demonstration:

```text
Camera A: local track 11
Camera B: local track 4
  -> one temporary global observation
  -> occupancy contribution = 1
```

Fusion must consider:

- Common floor and actual overlap geometry.
- Timestamp alignment and uncertainty.
- World-space proximity/reprojection consistency.
- Visibility and position uncertainty.
- Plausible speed and mutual exclusion.
- Optional appearance evidence where needed.

A temporary fused group must not contain two distinct simultaneous tracks from the same camera. Retain constituent local track references and association provenance. A bad or revoked merge must be correctable without rewriting raw track history.

Measure duplicate count error, false merges, false splits, reprojection error, synchronization sensitivity, ID consistency, and calibration sensitivity. Prove the controlled pair before expanding overlap groups.

### 10.3 Non-overlap and staircase association

Generate candidates only across legal portals/topology edges. Combine:

```text
appearance + exit zone + entry zone + elapsed time + direction
  + reachable topology + floor + mutual exclusion
```

Example: a track leaves a Floor 1 stair portal and a candidate enters the connected Floor 2 landing 8.2 seconds later. The elapsed time is an illustrative scenario, not a measured handover result or universal threshold.

Apply hard physical/topology gates before ranking appearance candidates. Require both an acceptance threshold and a margin over alternatives. These thresholds must be evaluated/calibrated on the fixture rather than described as identity probabilities.

### 10.4 Association state machine

```text
UNASSOCIATED -> CANDIDATE -> CONFIRMED
                      \-> UNKNOWN / EXPIRED
CONFIRMED -> REVOKED, if later evidence contradicts the hypothesis
```

- Retain candidate scores and reasons for rejection/acceptance.
- Preserve `UNKNOWN` when evidence is missing, weak, or ambiguous.
- If two people are similarly plausible, do not force a merge.
- Expire candidates after the configured topology-specific window.
- Store corrections as new events that reference superseded decisions.
- Clearly distinguish observed movement from inferred blind-gap continuity.

### 10.5 Temporary global identifier lifecycle

- Global IDs are random/opaque, visit- or demo-session-scoped hypotheses.
- They are not names, persistent identities, or biometric profiles.
- Raw `(camera_id, camera_epoch, local_track_id)` keys remain immutable.
- Configure hypothesis and appearance-gallery TTLs; expire visit data according to local retention policy.
- Do not present an uncalibrated score as `identity_probability`.

### 10.6 Selective appearance Re-ID

Appearance Re-ID is optional in early phases and may be enabled for the controlled gap scenario when needed. Baseline research selection: `kaiyangzhou/osnet`.

Use selective crops based on minimum dimensions, blur, visibility, occlusion, orientation utility, and update interval. Do not embed every person on every frame. Bound crop/embedding queues and batch sizes; discard low-value work before authoritative counting is affected.

Keep the embedding model behind a replaceable adapter. Store embedding provenance and TTL locally. Some OSNet weights have MSMT17 training provenance; record actual model/data terms in `THIRD_PARTY.md` rather than treating experimental availability as production clearance.

### 10.7 VSS gallery deferral

The full VSS Re-ID/gallery workflow may later provide CLIP-ReID, appearance retrieval, and reassociation after gaps. Evaluate it only if measured cross-camera errors justify Kafka/Milvus/etcd/MinIO and additional services. It is not required to pass the first demo.

## 11. Deterministic Crowd Analytics

Use `nvdsanalytics` or equivalent deterministic state logic for ROI occupancy, line crossing, direction, and overcrowding. Facility-level logic must remain explainable and versioned.

### 11.1 Count hierarchy

Expose distinct metrics:

1. **Camera-visible count:** Current valid person observations in one camera.
2. **Zone occupancy:** Unique observations in a configured zone after overlap/ownership rules.
3. **Floor-visible occupancy:** Unique visible observations across that floor's covered regions.
4. **Floor occupancy estimate:** Boundary/transition ledger reconciled with visible observations, where supported.
5. **Building occupancy estimate:** Initial occupancy plus external entries minus external exits, with coverage/quality.

Do not add overlapping camera counts. Use fused tracks or explicit authoritative-zone ownership. Global ambiguity should remain visible through unresolved counts/ranges instead of being hidden by an unjustified merge.

### 11.2 Entry/exit line crossing

Each boundary has a line/polyline, side convention, direction mapping, and ownership rule. Implement:

- Side-change hysteresis and a dead band.
- Minimum confirmed-track persistence.
- Direction and movement consistency.
- Debounce and per-track/per-boundary transition state.
- Deduplication across overlap owners, retracking, reconnects, and event replay.

Only a validated transition creates an IN/OUT event. A camera restart does not reset the building ledger or create an entry. Preventing duplicate counts after retracking may require a bounded local boundary-event association window; record its uncertainty.

Show `IN`, `OUT`, and current occupancy with time range/session and quality. Counter corrections must be explicit audited events.

### 11.3 Occupancy ledger and count conservation

For the building:

```text
expected_occupancy = initial_occupancy + external_entries - external_exits
```

Internal staircase movement transfers occupancy between floors; it does not increment building entry/exit totals.

For floor allocation, retain mutually exclusive categories for Floor 1, Floor 2, stair/in-transit, and unallocated people. Expose any difference between their sum and expected building occupancy as an allocation discrepancy. A person in transit must not simultaneously contribute to both floor allocations.

For reconciliation:

```text
discrepancy = expected_occupancy - visible_fused_occupancy - unresolved_not_visible
```

`unresolved_not_visible` must be a mutually exclusive ledger category for people not currently included in visible fused occupancy. Unknown camera associations alone do not justify creating extra people. Include blind-region/coverage uncertainty separately when it cannot be assigned reliably.

Illustrative accounting example, not a benchmark:

```text
Initial occupancy          120
Entries                    +18
Exits                      -10
Expected occupancy         128

Visible fused              126
Unresolved, not visible      2
Discrepancy                   0
```

Requirements:

- Track expected, visible, unresolved, discrepancy, coverage, and quality separately.
- Expose floor balances and people currently in a staircase/transition region.
- Prevent counting one person on both floors during a handover.
- Label incomplete-boundary results `ESTIMATED OCCUPANCY`.
- Never clamp a negative or inconsistent ledger silently; surface an anomaly and a correction mechanism.
- Do not automatically overwrite the ledger with visible counts to hide discrepancies.
- Record initial-occupancy changes, reset actions, and manual reconciliations.

### 11.4 Queue analytics

Configure queue polygons, optional centerlines, service boundaries, and relevant direction.

Track:

- Current queue size and membership quality.
- Joins, leaves, growth, shrinkage, and service throughput.
- Queue overflow and persistent boundary violations.
- Estimated wait time only where entry/service completion is sufficiently observable.

Queue membership uses geometry, persistence, and movement; a stationary diner is not automatically a queue member. Use a membership state machine with configurable join/leave dwell and temporary occlusion handling. Deduplicate members across overlap views.

When wait cannot be measured defensibly, show unavailable/insufficient observation rather than a made-up duration. Separate directly observed wait from throughput-based estimates.

### 11.5 Congestion

Use configurable, explainable combinations of:

- People per square metre, only with valid metric area/calibration.
- Average speed, dwell, throughput, queue overflow, and counterflow.
- Persistence windows and hysteresis.

Expose:

```text
NORMAL | BUSY | CONGESTED | SEVERELY CONGESTED
```

Each alert/state must include contributing measurements and threshold/rule revision. Without valid area, use an explicitly count-based/capacity-based rule rather than reporting people/m². Do not infer panic, injury, or intent.

### 11.6 Stair flow

Treat a staircase as an explicit facility region/transition, not an implicit floor jump.

- Measure Floor 1 -> Floor 2 and Floor 2 -> Floor 1 separately.
- Show rates such as `UP: n people/min` and `DOWN: n people/min` using an explicit rolling window.
- Distinguish visible stair crossings from inferred blind-gap handovers.
- Track people in transit so floor counts remain reconcilable.
- Ambiguous identity continuity must not prevent reporting a valid anonymous directional crossing when the crossing itself is observed.

### 11.7 Alerts

Required alert types include overcrowding, queue overflow, camera offline, frozen camera, timestamp anomaly, calibration warning, and occupancy discrepancy.

Alerts need stable IDs, severity, source/floor/zone, trigger evidence, rule revision, first/last occurrence, active/resolved state, acknowledgment state, and optional evidence references. Use debounce, cooldown, and deduplication to avoid alert floods. Acknowledgment does not resolve a still-active condition.

## 13. Persistence, Retention, and Local Evidence

### 13.1 Database

SQLite is acceptable for the demo. Use migrations, foreign keys, parameterized access, explicit transactions, and a repository/service interface compatible with later PostgreSQL migration.

Use WAL mode where appropriate, a bounded write queue, batch insertions for telemetry/snapshots, and indexes for time/camera/floor/event queries. Do not synchronously commit every frame or store raw video frames as database rows.

### 13.2 Required entities

| Entity group | Tables/entities |
| --- | --- |
| Runtime | `runs`, `cameras`, `camera_sessions`, `camera_health` |
| Facility | `floors`, `zones`, `portals`, `camera_calibrations` |
| Tracking | `local_tracks`, sampled `track_observations`, `global_track_hypotheses`, `association_candidates` |
| Analytics | `line_crossings`, `occupancy_snapshots`, `queue_snapshots`, `flow_events`, `congestion_events` |
| Operations | `alerts`, `alert_state_changes`, `evidence_clips`, `counter_corrections` |
| Provenance | `model_versions`, `tracker_versions`, `calibration_versions`, `configuration_versions` |
| Performance | `system_metrics`, `benchmark_runs`, `benchmark_artifacts` |

Relationships must preserve run/session, local-track keys, source event IDs, model/calibration/configuration revisions, and evidence references. Avoid destructive cascading deletion of evidence/provenance needed by retained events.

### 13.3 Retention

Configure separate retention for compressed recordings, evidence, crops, embeddings, track samples, event history, metrics, and logs. Document defaults and disk budgets in the runtime configuration.

Temporary global hypotheses and appearance galleries must have bounded lifetime. A reset command must clearly identify the temporary demo dataset/run it removes and preserve pinned models, calibration, and source footage.

### 13.4 Recording and evidence

- Preserve original compressed source streams/remuxed segments where practical.
- Use a bounded local rolling buffer for pre-event/post-event evidence.
- Generate clips for alerts, ambiguous transitions, debugging, and evaluation.
- Prefer keyframe-aware extraction/remuxing; document timestamp/keyframe boundary limitations.
- Re-encode only where a precise clip/preview requirement makes it necessary.
- Record source camera, time interval, timestamp basis, checksum, codec, path, and linked event IDs.
- Distinguish source evidence from separately rendered annotated evidence.
- Handle disk-full, missing segments, retention cleanup, and incomplete clips explicitly.

### 13.5 Database failure behavior

If persistence fails, expose degraded readiness and an alert. Use a bounded local durable spool where practical; once its capacity is exhausted, mark event completeness compromised rather than pretending full history exists. Detection/preview may continue if safe for the application's state, but the UI must reflect the loss of durable guarantees.

### 18.3 Initial engineering acceptance profile

| Item | Initial gate |
| --- | --- |
| Simultaneous demo feeds | Four enabled sources |
| Default analytics target | 8 FPS/camera; independently configurable |
| Sustained analytics cadence | At least 90% of each configured target over the accepted steady-state interval |
| p95 processing age | At most 2,000 ms receive-to-result in the real-time demo profile |

### 18.4 Why capacity must be measured

The following are workload calculations only:

```text
20 cameras x 25 source FPS = 500 decoded frames/second
20 cameras x 5 detector FPS = 100 detector frames/second
20 cameras x 10 detector FPS = 200 detector frames/second
15 people/camera x 20 cameras x 1 embedding/person/second
  = approximately 300 embeddings/second
20 streams x 2 Mbps = 40 Mbps = approximately 432 GB/day
20 streams x 4 Mbps = 80 Mbps = approximately 864 GB/day
```

These exclude some storage overhead and are not actual camera specifications or laptop benchmarks. They establish neither a twenty-stream capability nor a fixed maximum.

**Work:** Calibrate one pair, align time, implement MV3DT/equivalent fusion, define ownership, and evaluate errors/sensitivity.

**Gate:** A real person visible in both cameras contributes one occupancy observation; the controlled negative pair is not falsely merged.

**Work:** Configure portals/travel windows, use appearance selectively if required, combine topology/time/direction/zone evidence, and preserve `UNKNOWN`.

**Deliverables:** Raw metrics, benchmark reports, selected demo settings, measured acceptable operating envelope.

**Gate:** Capacity conclusions are measured on this GPU. Unattempted/unacceptable stream counts and stopping reasons are explicit.

**Work:** Freeze locks/models/engines/config, finalize instructions, cold boot, isolate outbound Internet, run the full demo and soak.

**Deliverables:** Offline acceptance report, final requirements checklist, installation/run/troubleshooting docs, demo script.

**Gate:** Every required laptop-demo criterion passes with local artifacts and real GPU perception.
