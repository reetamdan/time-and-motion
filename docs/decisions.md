## Historical implementation boundaries (2026-10-23)

These statements are retained as the original record. The next section supersedes conflicting statements only for the 2026-10-26 single-camera smoke scope.

- This documentation/orchestration layer does not implement a DeepStream pipeline, detector export, tracker, known-positive validator, replay engine, or benchmark collector. Those require application/perception implementations and real evidence.
- No default replay or benchmark runner is guessed. Their wrappers validate arguments/assets and preserve runner output, then block/fail if real result evidence is absent.
- The current model configuration initially has `selected_model: null` and disabled candidates. Until an enabled model is selected with pinned artifacts, strict preflight and a frozen GPU demo remain blocked.
- Authorized camera clips, provenance, checksum sidecars, reference labels, surveyed calibration, and model/engine artifacts are operator/project inputs; documentation does not invent them.
- Backend/frontend/configuration files may provide useful local UI/API behavior, but file existence and process readiness are not GPU, analytics, capacity, or offline acceptance.
- `scripts/offline-test/run.sh` checks local files and invokes the project configuration loader when available. It does not reboot, isolate a network, observe external traffic, start a soak, or issue an acceptance certificate.
- `scripts/reset-demo.*` relies on the documented endpoint to preserve models/config/calibration and clear only run-scoped temporary state. The scripts themselves perform no filesystem deletion.

## Scoped streaming transport and EOS/replay supersession (2026-10-26 12:25 UTC)

- The current Service Maker bridge streams each real extractor frame over stdout as `AEGIS_FRAME_V1:` followed by its schema-1.0 JSON payload. The same record is written to the per-epoch JSONL artifact; no missing/past frame, detection, track ID, PTS, or replay frame is synthesized. Non-prefixed output and stderr remain log evidence.
- Stdout consumption uses a bounded 128-frame queue. While the session is active, a full queue makes the reader retry rather than grow unboundedly, providing backpressure. After natural stdout EOF, the reader marks completion and the consumer drains all remaining queued frames before exiting; this normal-EOS drain is distinct from cancellation during operator stop.
- Per-epoch `.jsonl`, `.summary.json`, and `.log` paths remain part of the runtime evidence contract. JSONL and logs can retain partial output after an early stop; a final run summary requires the extractor to reach its summary-writing path and is not invented when absent. The replay report's second epoch, intentionally stopped after a fresh positive count, has JSONL/log evidence but no final summary.
- `reports/validation/live-eos-replay-cam01/result.json` passes all 28 declared checks. For the first epoch it proves a positive count before natural EOS, clean 710-frame completion and contiguous JSONL, natural-EOS container absence, 710 backend-consumed frames with an empty drained queue and no reader/consumer error, stale null count/FPS fields with `DEGRADED` health and increasing age, a still-active run, and operator stop followed by confirmed container absence. It then proves a distinct second epoch with a fresh positive replay count, a second stop, both exact epoch containers absent, completed TestClient shutdown, and no remaining adapter sessions.
- This supersedes only the former lack of live natural-EOS/stale/replay evidence. The second epoch is not a full-clip run; one observed second stop took about 22.719 seconds and is not a latency or performance pass. External browser/production-socket behavior and unexercised startup, reader/consumer-failure, forced-termination, and production-process crash cleanup paths remain unproven. No accuracy, calibrated analytics, or candidate-baseline claim is added.

## 2026-10-26 detector-candidate diagnostics

- Reference frames for detector parity must be decoded with the stream's tagged colour matrix. `demo/cam01.mp4` is BT.709 limited range; the earlier OpenCV PNG references were BT.601-decoded (`reports/model-evaluation/rt-detr/diagnostics/result.json`). New references use ffmpeg with an explicit BT.709/tv conversion.
- DeepStream 9.2 nvinfer resizing (default and `scaling-filter=1`) measured closest to top-left nearest sampling at 1920x1080 -> 640/512, not to HF bilinear resizes. RF-DETR therefore uses a full-frame 1920x1080 network input with the HF resize and mean/std inside the ONNX graph (requires 1920x1080 nvstreammux output). RT-DETR's closest nvinfer option is `scaling-filter=3`; it was evaluated diagnostically only and the candidate config is unchanged.
- The production TrafficCamNet config also uses nvinfer's default scaling filter. This has not been changed; evaluate it before any accuracy work.
- RF-DETR raw output slots are order-sensitive: near-tied two-stage proposal scores (gaps ~1e-6) reorder under rounding-level differences between backends. Raw-slot parity, query-order parity and order-independent strict person-set parity are reported separately; none replaces the strict end-to-end crosscheck, which still fails for both candidates. These mechanisms were demonstrated on two sampled frames; they do not establish general backend equivalence, and the strict crosscheck sensitivity shown there is not a proof that only bit-identical preprocessing can pass. Corrections: `reports/model-evaluation/*/conclusion-corrections.json`.


## 2026-10-26 lifecycle: stop latency and analytics rate

- DeepStream containers run with `docker run --init`. The image entrypoint is a bash script that does not `exec`, so as PID 1 it ignored SIGTERM and every stop waited Docker's full grace period.
- The backend keeps draining the Service Maker stdout pipe after a stop until EOF. Otherwise `wsl.exe` blocks on a full pipe and cannot exit. Together with `--init` this took the mid-run operator stop from 22.7 s to about 0.8 s (`reports/validation/stop-latency/result.json`; live EOS/replay 28/28 PASS).
- `analytics_fps` is frames consumed over a 2 s high-resolution window (reported only once ≥ 0.5 s is spanned). The per-frame monotonic-delta estimate was undefined at Windows clock-tick resolution.
- The demo file pipeline runs unpaced (`sync=False`): about 365 frames/s against a 29.97 fps source. Freshness, counts and history therefore advance about 12× faster than real time during replay. This is not a live-camera timing result.
- TrafficCamNet nvinfer scaling is sensitive: the default (nearest-like) vs bilinear vs supersample changes persons/frame by up to ~14% and shifts boxes 11–20 px. The production config is unchanged pending labeled evaluation (`reports/validation/trafficcamnet-preprocessing/result.json`).

## 2026-10-26 single-camera workflow, time model and lifecycle hardening

- **Time domains.** `Observation.timestamp` for real cameras is source/event time: PTS seconds within the camera epoch (`backend/app/analytics/timebase.py`). Receive time (monotonic, plus UTC for display) drives only freshness and transport diagnostics. No UTC capture time is derived from file PTS. A backward or >2 s forward PTS jump opens a new segment; time-dependent analytics reset at segment and epoch boundaries.
- **Replay modes.** In `paced` mode the backend consumer releases frames on the PTS schedule, with a 16-frame queue so backpressure reaches the unchanged, hash-pinned extractor. `unpaced` mode is for evaluation and benchmarks. Measured: 0.997 vs 12.4 source s per wall s.
- **Camera-local analytics** (`backend/app/analytics/camera_local.py`) persist source-time visible-count history and optional `image_pixels` line crossings. They are idempotent per run/camera/epoch/segment/bucket and per crossing key. Image-space lines are a separate `coordinate_space` from `floor_map` boundaries. They never feed building entries/exits, occupancy or `world_position`.
- **No crossing for cam01.** The clip pans by a cumulative 1308 px horizontally, so a fixed pixel line would count camera motion (`reports/validation/cam01-camera-motion/result.json`).
- **Ownership-aware cleanup.** Only names matching `aegis-[A-Za-z0-9_.-]+` are touched, by exact name. The sequence is stop → verify absent → bounded kill/rm → verify. An unconfirmed release is kept as an unresolved record, blocks a restart of that camera, and surfaces as run status `STOP_FAILED` plus a CRITICAL alert. The next stop retries it.
- **Event loop.** Adapter availability probes (three `docker run` calls, about 16 s) and snapshot building run in worker threads. Snapshots use the cached probe result. Before this fix, a start blocked the consumer for 6.7 s.
- **Evidence directories.** Live validators always create a fresh directory and refuse existing ones (`scripts/lib/evidence_dirs.py`).
- **Perception determinism.** Two runs of the pinned FP16 TensorRT + NvDCF pipeline on the same clip agree on only about 77–84% of frames. Exact paced/unpaced equality is therefore not a valid real-data test of the analytics. Wall-clock independence is instead checked by replaying recorded real detections at two speeds, and exact output determinism is left as an open AC-24 question.
- PRD status is maintained in `docs/acceptance-matrix.md`.

## 2026-10-27 ownership, restart recovery and end-of-stream completion (review follow-up)

- **Ownership before launch.** The supervisor records `owned_resources` (run, camera, epoch, adapter, exact resource name, runtime, state `LAUNCHING`→`ACTIVE`→`RELEASED`/`UNRESOLVED`) before calling `start_camera`. Adapters raise `PerceptionStartError(resource_allocated=...)`: a failure before launch releases ownership immediately. A failure after launch is reconciled through `stop_camera`, and if unconfirmed it stays owned, alerted and retryable. Reproduced before the fix: `reports/validation/review-repro-cleanup-ownership-pre-fix/`; after: `...-post-fix/`.
- **Restart recovery.** `recover()` replaces `initialize()`. Unreleased rows are adopted by the adapter (DeepStream accepts only the exact name it would generate for that camera/epoch/runtime) and given one bounded release attempt. Runs are marked `STOPPED` only after confirmed release; otherwise a `STOP_FAILED` run is restored and blocks starts. Verified on real hardware with an abandoned running container (`live-workflow-cam01-20261026T184501506952Z`).
- **Clean EOF completion.** The consumer classifies its end (`CLEAN_EOF`, `ABNORMAL_TERMINATION`, `CONSUMER_FAILED`; nothing for an operator stop or cancellation). `CLEAN_EOF` flushes the final history bucket immediately; flushing pops the analytics engine, so a stop cannot duplicate it. Reproduced: 15/30 frames before stop (`review-repro-eof-flush-pre-fix`); after the fix: 30/30.
- **Replay evidence wording.** The earlier recorded-replay check varied only supplied receive timestamps. It is renamed accordingly, and real delivery speeds are now tested through the real consumer and pacer with real waits (correction: `live-workflow-cam01-20261026T173819981704Z/scope-correction.json`).
- **Dashboard.** At widths of 901–1450 px the run-status badge was hidden by CSS, so `STOP_FAILED` was invisible. It is now always shown, and the browser check covers 4 widths. History is labelled current vs previous epoch. Building entries/exits are null (not 0) without a calibrated active boundary.
- **Acceptance matrix.** AC-24 is about locks, hashes and manifests (BLOCKED only on calibration manifests); determinism is a separate observation. AC-25 is now evidenced by executing the documented commands. AC-25 and AC-26 are split into independently proven parts.

## 2026-10-27 completion pass: contracts, identity, startup, evidence, profiles, geometry, load

- **Start over STOP_FAILED returns 409 `CLEANUP_UNCONFIRMED`** (it used to return 200 with the old snapshot). A refused start must not look like a successful one. A healthy active run keeps idempotent 200 behaviour, and reset uses the same 409.
- **Artifact identity is three separate facts.** For every runtime artifact (checkpoint, engine, infer config, parser `.so`, tracker, wrapper, extractor, capability probe, image reference) there is the recorded expected sha256 (`configs/models.yaml`), the hash recomputed from disk, and their comparison. A recomputed hash with nothing recorded is `NO_EXPECTED_IDENTITY` and blocks; it is never an implicit pass. The tracker's sha256 is now required whenever the tracker is enabled.
- **Capability cache instead of per-start probes.** A single container probe (`scripts/lib/capability-probe.sh`) replaces three or more. Its result is fingerprinted by the docker image ID, the image reference, the current wrapper, probe and extractor hashes, and the distro. It is reused only after a cheap liveness check (`docker image inspect`). It expires after `max_age_seconds`, is discarded on liveness failure, fingerprint change, an observed start failure, or an operator request, and failures are never persisted. Measured: about 16 s cold start, about 5 s warm (`startup-evidence-cam01-20261027T163250116208Z`). The remainder is container launch, engine deserialization and the first metadata frame.
- **Startup cancellation.** A start cancelled after launch reconciles its resource (shielded) before propagating. `stop()` also releases any unreleased ownership row of the run, so a resource can never be owned but untracked.
- **Long history.** The history API returns the newest window by default, pages with a cursor, and downsamples within segments. Before this, the chart froze after 2000 samples because the query returned the oldest rows.
- **Evidence timeline alignment.** On cam01, DeepStream's first-frame PTS is 0.0667 s while ffmpeg's is 0.0, because of the H.264 B-frame reorder delay; frame indices are identical. Evidence maps pipeline time onto the file by aligning the epoch's first decoded frame, and records that mapping. Validation compares the snapshot with an independent decode of the pipeline's `frame_number`: PSNR ∞, against 20.3 dB for the frame two later. The first live run (2 frames late) is preserved with a correction note.
- **Clips are stream copies.** There is no re-encode, and a clip starts on a keyframe, so both the requested and the actual bounds are stored. Snapshots are accurate decodes. Evidence is extracted from the original source file, which works for file replay. Live RTSP evidence would need a recording ring buffer (future work).
- **Detector profiles are configuration.** `runtime_profile` covers the infer config, parser, explicit person-class normalization (2 for TrafficCamNet, 0 for the candidates), frame geometry and its policy, and top-k. The candidates are enabled as `candidate_unaccepted` and can only be selected with `selection_mode: candidate_evaluation`. The default selection is unchanged. The protected extractor is unchanged; geometry is passed through its existing arguments.
- **Geometry gating.** A `VALID` calibration requires a matching file (camera, floor, revision) whose held-out validation passes, checked at load. At runtime the first frame's size must equal the calibration's `image_size` and each image line's `frame_size`; otherwise that geometry is disabled for the epoch and a `geometry-invalid` alert is raised. Facility analytics (`analytics/facility.py`) wire the existing zone, fusion, queue, congestion and ledger engines on calibrated foot points only. Metric fusion and density also require `meters_per_unit` and a shared `replay_group`. Each unavailable capability reports its exact reason.
- **Concurrent camera starts.** Cameras start concurrently and each fails in isolation. A slow camera no longer delays the others (before this, starts ran serially at about 5 s per camera).
- **Load ladder.** Duplicate-input feeds of the single clip are labelled in the generated configuration and in the reports. Results are one pass per step, with no steady-state window and no extrapolation. Windows `nvidia-smi` attributes the WSL container's GPU and NVDEC load; medians are diluted by start-up, so p95 values are reported.
- **Labelled evaluation.** Proposals are never ground truth. The evaluator refuses files that are not REVIEWED by a named reviewer, and files whose boxes are identical to a proposal file. A decision rule is frozen in `scripts/evaluation/evaluation-settings.json`.

## 2026-10-27/28 facility freshness, extractor v2, UI, live sources, routes, capacity

- **Facility contributions carry two clocks.** Each camera's latest calibrated frame is kept with its source time (+ `timestamp_offset_ms`) and its receive (monotonic) time. A contribution is current only while the camera runs, has a runtime-valid calibration, has produced a frame in this epoch, its stream has not ended, and the frame was received within `health.stale_after_ms`. Otherwise every dependent zone, floor and building figure becomes `UNAVAILABLE` with the reason, never the last value and never 0. A 1 s timer evaluates even when no frame arrives. Epoch change and source-segment discontinuity reset queue dwell, crossing tracks, portal presence and congestion persistence for that camera. Evaluation is throttled per camera on that camera's own source time; one shared throttle re-armed on almost every frame with several cameras whose timelines differ.
- **Floor/building counts are de-duplicated memberships, never zone sums.** Zone counts may overlap (a queue inside a dining area). The floor figure is the union of zone members by camera-local track, fused across cameras only through a validated overlap group (shared replay group, metric scale, freshness, agreeing source times). Ambiguous fusion keeps people separate and marks the figure `ESTIMATED`; it never forces a merge. Floors are distinct in the building sum.
- **Stair transitions.** A track that disappears inside a portal endpoint zone becomes a departure; a track first seen inside the other endpoint zone is an arrival. Arrivals are associated with departures within the portal travel window through `TopologyAssociation`. Without a re-identification evidence score the decision is always `UNKNOWN` and is persisted as such. Flow counts arrivals as `inferred` (`observed_count` 0) with quality `ESTIMATED`; it is never presented as an observed physical crossing.
- **Extractor v2 instead of editing v1.** v1 (`6093b5d5…`) is the frozen historical baseline and stays byte-identical. v2 adds source-side pacing for paced file replay (measured: failure visible after 0.72 s instead of 11.48 s; 19 instead of 343 frames delivered after a producer kill), schema 1.1 `emitted_unix_ns` (producer wall clock; container and host clocks are reported separately and never mixed with source time), `--stage decode|detect|track` for benchmarks, and live `rtsp://` input. Every v2 change is a new recorded identity in `configs/models.yaml`, with history in a comment there; a changed hash is never re-blessed silently.
- **UI on an adapted design system.** OpenIntelligentUI (MIT, revision `8391a94c`) tokens, form styles, drawer, chip filter, panels and chart config are adapted into `frontend/src/design-system/` (provenance table in `NOTICE.md`). Not adopted: the CopilotKit runtime, generative UI, CDN imports, hosted models, PostHog or launch telemetry. There is no assistant and no external request. `backdrop-filter` and animated blur blobs are dropped because panels overlay live video. Fonts are bundled. Run status, connection, replay mode and Start/Stop/Reset stay visible at every width. `STOP_FAILED` adds a banner with Retry cleanup, and a refused start (HTTP 409 `CLEANUP_UNCONFIRMED`) is shown as a refusal, not a failure of the app.
- **Two host routes, one adapter.** `windows-wsl` (validated, default): a Windows backend reaches docker through `wsl.exe -d Ubuntu-22.04 --` (superseded 2026-10-28: `-e`, see session 7 below). `linux-docker`: the backend runs inside WSL (or native Linux such as the future A6000 host) and calls docker directly. The command, cleanup, capability probe and telemetry differ only in that prefix. The WSL route uses a project-local, checksum-pinned toolchain (`scripts/setup/install-wsl-toolchain.sh`): uv-managed CPython 3.12 (Ubuntu 22.04's 3.10 is below the pinned packages' floor), Node 24.14.1 and static ffmpeg. No apt package of the existing distribution is changed. The frontend is built in an isolated copy so a Linux `npm ci` never replaces the Windows `node_modules`.
- **Live (RTSP) sources are configuration only.** `source_type: rtsp` with an `rtsp://` URL. Credentials are given as `${VAR}` references resolved from the backend environment at launch, are never stored or logged, and are redacted from any log tail that can reach an alert or the API. A live stream ending is a source loss (`ABNORMAL_TERMINATION`), never a clean EOF. The camera reconnects with a new epoch after a capped exponential backoff (`health.reconnect_backoff_seconds` doubling to `max_reconnect_backoff_seconds`). A stall watchdog (`health.live_stall_seconds`) releases and reconnects a live camera that stops delivering frames. Other cameras are unaffected. Live sources have no preview and no evidence clips (`evidence_available: false` with the reason): clips need a local recording ring buffer, which this version does not implement. File replay remains the demo scope (PRD §5).
- **Capacity protocol (PRD 18.3/19), declared before measuring.** The paced real-time profile, a 120 s warm-up plus a 600 s measured window, and 3 repeats per condition. Stages A–C run duplicate containers without the backend; stage D runs the real backend with all analytics. Per-feed gates: cadence ≥ 90% of the configured 8 fps analytics target, p95 processing age ≤ 2000 ms, backlog growth < 500 ms, no frame gaps, no crash, cleanup confirmed. The source rate (29.97 fps) and resources are reported, not gated. Load data is the labelled repeated clip `demo/derived/cam01-repeat33.mp4`. Duplicate feeds measure load only, never coverage or accuracy. Stages E–G need calibrated overlap footage, Re-ID, or an accepted core profile and are reported as not run.
- **Detector numerics.** Engine-in-DeepStream and parser parity pass on identical tensors. The strict cross-pipeline check stays FAIL and is not relaxed. It also fails between two CPU references that differ only in colour matrix, so it measures sensitivity in a dense low-confidence crowd, not an implementation defect. ## 2026-11-04 RTX A6000 workstation

- **A generated hardware profile, not edited configs.** `configs/a6000/` and `perception/deepstream/a6000/` are generated from `configs/` by `scripts/a6000/configure.py` (`generate | check`) and carry a do-not-edit header; `tests/test_a6000_profile.py` fails when they drift from `configs/` or from the engines' hashes. The laptop configuration stays unchanged, and `Start-Aegis.cmd` selects the profile only when `nvidia-smi` reports an RTX A6000.
- **RT-DETR FP16 is selected on the A6000 but stays unaccepted.** It tracked ~68 people per frame on the dense demo clip versus ~17 for TrafficCamNet, and FP16 reproduced the FP32 boxes (99.4 % matched at IoU >= 0.5) at 2.4 ms versus 5.1 ms. More boxes and FP16/FP32 agreement are not accuracy: `selection_mode: candidate_evaluation` and the *Candidate · unaccepted* label remain until human-reviewed labels are scored.
- **Continuous file replay (`loop: true`).** DeepStream `file_loop` keeps PTS and `frame_number` monotonic across wraps (one ~0.1 s PTS step), so a looping epoch stays one source segment. The backend maps pipeline frame *n* to file frame *n* mod the file's frame count (ffprobe header, else a packet count; decoding the whole file was measured 27x slower and delays start). Evidence maps a time only inside a pass whose first frame was observed and refuses otherwise (`SOURCE_LOOP_UNMAPPED`). The per-epoch frame log rotates at `replay.frame_log_max_mib`.
- **The boxes overlay is display only.** `GET /cameras/{id}/detections` serves the last ~150 frames of tracked boxes; the browser aligns them to the preview by file position, scopes its cursor to the camera epoch and clears boxes 1.5 s after the last fresh poll. Counts and history never come from it.
- **One shared SQLite connection.** Opening and closing a connection per call cost ~14-16 ms (WAL checkpoint/fsync on close) and made multi-camera start latency flaky; one connection reused under the repository lock with `synchronous=NORMAL` costs < 1 ms. Evidence ordering ties are broken by insertion order (`rowid`).
- **WSL is kept running by the launcher.** WSL stopped its VM within 4 idle minutes (measured; same test with the keep-alive: no restart), taking Docker down. `scripts/a6000/start.ps1` holds one tagged `wsl.exe ... sleep infinity # aegis-keepalive-<checkout hash>` attached to its console for the server's lifetime and waits for Docker before serving; global WSL settings are not changed.
- **One backend per database (OS lock).** Startup recovery releases every resource the database lists as owned, so a second backend on the same database, even on another port, would stop the first one's cameras. The backend takes an exclusive OS lock on `<database>.lock` before migrations and recovery and holds it for its lifetime. A PID file was rejected because it can go stale and PIDs are reused; the OS drops the lock when the process dies, including a crash.
- **Evidence groups are atomic.** A marker's snapshot and clip are inserted in one transaction and evicted together. The marker just captured is never evicted, so the API cannot return half a marker or nothing even under `max_records: 1` or a byte budget smaller than one clip. Registration and retention are serialized.
- **Benchmarks select a profile explicitly and keep complete logs.** `run_capacity.py --config-dir` (else `CCTV_CONFIG_DIR`) is used for every stage. Rotation is a production storage bound, not a benchmark policy: the benchmark disables it and refuses a rotated log rather than measuring a truncated window.
- **Camera start-up has its own deadline.** The first-frame deadline reused the telemetry command timeout (`max(15 s, ...)`). Concurrent starts on the A6000 took 16 s for eight cameras, so the first capacity ladder failed every camera at 4 feeds. `replay.startup_timeout_seconds` (60 s) bounds only a slow or hung start; a failing pipeline exits and is reported at once.
- **Retention prunes by age, then by size, and never inside a run's totals.** A periodic pass (startup + every `cleanup_interval_minutes`) deletes time series after `metrics_days` and history after `event_history_days`, keeping the newest snapshot per scope so current values never vanish. Facility line crossings and the events they reference are never pruned inside a run: the dashboard's entries/exits totals count them, and `events` deletes cascade into `line_crossings`. Whole stopped runs leave after `event_history_days`, except the newest run and any run that still owns an unreleased container. Over `max_database_mib` the time-series window halves (floor 30 min), then a `storage` alert opens; data in use, not file size, is measured, because SQLite reuses freed pages without shrinking the file. Deletes run in 2,000-row transactions on the shared connection so analytics writes wait milliseconds, not seconds.
- **Reduced analysis rate by decoder drop, opt-in per camera.** `analysis_frame_interval: N` sets `nvurisrcbin` `drop-frame-interval`, so inference, tracking, the probe, JSON and the backend all run at source fps / N. nvinfer `interval` was rejected: it skips only inference, while the tracker, JSON and backend still run at 30 fps, and at 8 feeds the host CPU was as saturated as the GPU. Pyservicemaker's `batch_capture` forwards only `file-loop` to the source, so the extractor sets the property on the source element it created (`batch_capture-source-0_0`) before the pipeline starts and records the value read back. The default stays 1 because 8 cameras fit at full rate and the accuracy cost is not measured. (Measured on the demo clip at N = 4: 7.5 fps, contiguous frame numbers, 261 distinct track IDs against 478 at full rate; whether that means fewer ID switches or lost tracks needs labels.)
- **Cameras load in waves; a refused start fails at once.** 16 pipelines loading together on the A6000 failed decoder and TensorRT allocations with most of the GPU free, and Service Maker then blocks after `Unable to set the pipeline to the playing state` instead of exiting, so each camera waited the full 60 s deadline. `replay.startup_concurrency` (default 4) caps pipelines loading at once: a semaphore around each camera start, held until its first frame or failure, so starts overlap but never all at once. The startup wait scans the container log once a second for that line and fails the start with the log's cause lines, freeing its GPU resources. The 12-pipeline WSL2 limit found next is not worked around: a 13th camera fails at once and visibly.
- **Several file cameras per pipeline, opt-in.** WSL2 grants this A6000 at most 12 DeepStream pipelines, so one container per camera capped the site at 12. `replay.cameras_per_pipeline` batches compatible file cameras (same loop and analysis interval) into one container and `nvstreammux` batch. nvinfer is pinned to batch-size 1, so the verified batch-1 engine runs each frame instead of DeepStream silently building an unpinned batch engine from ONNX. Each camera keeps its own epoch and consumer; the shared container is recorded for every member before launch (crash recovery adopts the exact `aegis-batch-<epoch>` name), a stop detaches one camera and the last stop releases the container. Fault isolation becomes per pipeline, so the default stays 1 and live cameras never share. Measured: 20 cameras at 4 per pipeline.
- **CI without the GPU or LFS data.** `.github/workflows/checks.yml` runs `scripts/check.py` on Windows and Linux with `lfs: false`; Git LFS pointer files count as missing artifacts, so their tests skip with a reason. GPU validation stays a workstation step.
