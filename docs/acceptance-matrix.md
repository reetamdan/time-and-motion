## How to read this

**Overall** is the status of the *whole* criterion, as the PRD words it. A criterion is `PASS` only when its full pass evidence exists; a single working component does not make a broad criterion pass.

| Status | Meaning |
| --- | --- |
| `PASS` | The PRD's pass evidence exists for the full criterion, within the stated scope |
| `FAIL` | Tested, and the criterion was not met |
| `BLOCKED` | Cannot be completed without a concrete external input (footage, labels, calibration, hardware) or an explicit user constraint |
| `NOT_RUN` | Feasible now, but not yet executed. This is unfinished engineering, not an external blocker |

Five evidence tiers are kept separate, so that a lower tier is never presented as a higher one:

| Tier | Meaning |
| --- | --- |
| **U** | Unit/regression tests (synthetic or controlled inputs) |
| **I** | Real integration on this laptop: real GPU, container, API, and browser, on `demo/cam01.mp4`. A duplicate-input run (the same clip under several camera IDs) is labelled as such |
| **N** | Detector numerical consistency: same-input engine/parser parity, and cross-pipeline agreement |
| **L** | Labelled task accuracy (needs human-reviewed ground truth) |
| **M** | Multi-camera / calibrated-geometry acceptance on real, physically distinct footage |

`–` means the tier does not apply to the criterion.

Rows with an `a`/`b` suffix split one PRD criterion into parts that are proven independently. AC-25 is split by documented route; AC-26 into design/procedure and on-A6000 validation. No new requirements are added.

## Separate, non-acceptance observations

- **Inference determinism.** The pinned FP16 TensorRT + NvDCF pipeline is not bit-deterministic between runs. This is outside AC-24 (artifact reproducibility). In the three timed runs per profile, the mean visible counts varied by ≤ 0.07.
- **Paced file replay buffering.** 2026-10-27: beyond the 16-frame backend queue, about 12 s of frames sat in the WSL pipe relay in paced replay. Extractor v2 then added producer-side pacing (`--pace source`, 200 ms lead; paced-lead run: lead at kill < 1 s, failure visible within 3 s). 2026-10-28: that pacer timed frames on the WSL guest's monotonic clock, which runs 2.2–3.5 % fast against the host, so on long runs the producer drifted ahead (~20 s per 10 min in capacity stage C) and was then held back only by queue/pipe back-pressure. The WSL wall clock alone was not enough (time sync steps it back every ~30 s); the current extractor `4ef4f94a…` paces on a host-time estimate and its paced re-validation passed (paced lead, live workflow, capacity stage A r1/r2 checked against host time).
- **Detector outputs differ widely** on the same clip (mean visible per bucket: TrafficCamNet 17, RF-DETR 39, RT-DETR 68). Without labels this says nothing about which detector is better.
