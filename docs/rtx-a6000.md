# RTX A6000 workstation profile

The project runs on its target deployment, an RTX A6000 workstation, with a dedicated profile in `configs/a6000/`. It is generated from `configs/` by `scripts/a6000/configure.py` and is selected automatically by `Start-Aegis.cmd` when an RTX A6000 is detected. The upstream `configs/` (laptop, RTX 5070 Ti) are unchanged.

Validated on 2026-11-04: Dell Precision 5820, NVIDIA RTX A6000 (48 GB, sm86, driver 596.71), Windows 10 Pro for Workstations, WSL2 `Ubuntu-22.04`, Docker Engine 29.9.2 with the NVIDIA Container Toolkit 1.20.1, the pinned DeepStream 9.2 image (TensorRT 10.16).

## Start

Double-click **`Start-Aegis.cmd`** (or run it from a terminal), then open **http://127.0.0.1:8000/** and click **Start demo**. Keep the window open; **Ctrl+C** stops the server. `Start-Aegis.cmd -Dev` starts the development UI at http://127.0.0.1:7100/ instead.

Stop a server started in the background with `.venv-windows\Scripts\python.exe scripts\a6000\stop-server.py` (it stops the demo first and refuses to touch any other process on the port).

Runtime state (SQLite database, evidence, capability cache) is kept in `.install\a6000\state`, outside the repository's checked-in historical databases. Set `CCTV_CONFIG_DIR` to override the profile.

## What the profile changes

| Setting | `configs/` (laptop) | `configs/a6000/` | Why (measured on the A6000, `reports/a6000/optimization-receipt.json`) |
| --- | --- | --- | --- |
| TensorRT engines | sm120 engines | sm86 engines built on the A6000 | Engines are GPU-architecture specific |
| Selected detector | TrafficCamNet (provisional smoke) | **RT-DETR, FP16 engine** (`candidate_evaluation`) | On the crowded demo clip: ~68 tracked people per frame vs ~17 for TrafficCamNet (RF-DETR: ~40) |
| RT-DETR precision | FP32, strongly typed | **FP16** | 2.4 ms vs 5.1 ms per frame; reproduces the FP32 boxes (99.4 % matched at IoU >= 0.5, mean IoU 0.994, 72.3 vs 72.5 detections per frame) |
| `cam-01` replay | once (ends at 23.7 s) | **`loop: true`** | The dashboard stays live until Stop instead of going stale at the end of the clip |
| Tracker | NvDCF perf | unchanged | `maxTargetsPerStream` 150 vs 300 gave identical tracks on this clip |

RT-DETR stays labelled *Candidate · unaccepted* everywhere: no human-reviewed accuracy evaluation exists yet (`docs/annotation-guide.md`).

Measured results with this profile:

- Paced demo, 5 minutes: 12 passes of the clip, 29-30 fps, 60-78 people in view, a flat ~225 ms backend queue, 601 contiguous history samples.
- Unpaced, the full application path (decode, detector, tracker, analytics, persistence) runs ~220 fps for one feed.
- Detector throughput in the pipeline (unpaced, decode + detector + tracker): TrafficCamNet 496 fps, RT-DETR FP32 165 fps, RF-DETR FP32 139 fps.

## Rebuild, regenerate, validate

The sm86 engines are in Git LFS (`git lfs pull`). To rebuild them on an A6000 (existing engines are kept; delete one to rebuild it):

```powershell
wsl -d Ubuntu-22.04 --cd "$PWD" -e bash scripts/deepstream.sh bash /workspace/scripts/a6000/build-engines.sh
.venv-windows\Scripts\python.exe scripts\a6000\configure.py generate   # re-pins engine and config hashes
```

After any change to `configs/*.yaml` or an infer config, run `configure.py generate` and commit the result; `tests/test_a6000_profile.py` (and `configure.py check`) fail while the profile is out of date.

Validation on the A6000:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\a6000\validate-profiles.ps1
# with the server running (Start-Aegis.cmd):
.venv-windows\Scripts\python.exe scripts\a6000\validate_browser_loop_overlay.py
```

- `validate-profiles.ps1`: each detector profile runs the full clip on the GPU (looping off): 710/710 frames, positive counts, source-time history, a real evidence snapshot and clip, a clean stop and confirmed container removal. Evidence: `reports/validation/a6000-profiles-<UTC>/`.
- `validate_browser_loop_overlay.py`: a paced run in headless Chrome for 40 s, past the end of the clip: the camera stays live, the boxes overlay is painted, the preview stays within 1 s of the pipeline (measured ≤ 0.2 s), and Stop releases the container. Evidence: `reports/validation/a6000-browser-loop-overlay-<UTC>/`; `--readme-screenshots` also copies the screenshots under `reports/ui/`.
- `validate_overlay_recovery.py`: starts an isolated backend on port 8779 with fresh local state, checks loop evidence, injects an overlay-only HTTP failure, checks recovery and epoch cursors, then exercises unpaced playback at 390 px. Evidence: `reports/validation/overlay-recovery-<UTC>/`. Repeatable runs: `reports/validation/overlay-recovery-20261103T213228598288Z/result.json` (17/17, with source hashes) and, after the follow-up review changes below, `reports/validation/overlay-recovery-20261103T215127357311Z/result.json` (17/17). The preceding validator preflight failure and its explanation are retained in `overlay-recovery-20261103T213142212839Z`; no camera pipeline started in that failed preflight.

## Independent review and improvement priorities — 2026-11-04

The local history and GitHub matched at `984f439` after fetching. The two workstation commits add looping/overlay/SQLite reuse (`4cf4070`) and the reproducible A6000 profile (`984f439`). The review checked their source changes, project-local development transcripts and committed measurements. GitHub had no issues, pull requests or workflow runs at review time.

Corrections implemented:

- Detection polling now scopes cursors and in-flight responses to the camera epoch. Failed requests time out, and boxes expire even while WebSocket snapshots remain live. Equal-position matches prefer the newest replay pass.
- Evidence mapping refuses unobserved loop boundaries instead of silently reusing an older pass. The frame-count fallback (no header count) stays a packet count: an MP4 header's `nb_frames` is itself a sample count, and decoding the whole file (`-count_frames`, 5.4 s vs 0.2 s for the demo clip) would delay the camera's start and time out on long MKV/TS recordings.
- `scripts/check.py` runs the fast checks with isolated runtime paths. GitHub Actions runs Windows/Linux checks without downloading historical LFS data. Asset checks distinguish LFS pointers from binaries and detect an individually missing A6000 engine. The workflow will first run after these changes are pushed.

Recommended next measurements, in order:

1. **Accuracy:** review the existing annotation package, then measure precision/recall/count error for all candidates on the same frames. More tracked boxes does not prove fewer counting errors; FP16/FP32 agreement measures numerical consistency only. Existing strict cross-pipeline disagreements remain disclosed in `reports/model-evaluation/numerical-status-20261028.json`.
2. **Capacity:** run the existing supervised ladder and 30-minute soak against the A6000 profile, preserving per-feed latency, memory and cleanup results. A single stream at ~220 fps does not establish seven simultaneous 30 fps streams.
3. **Long-running storage:** the 256 MiB rotation bound applies to each epoch's frame log (plus its previous file). Old epochs and database history need measured retention before an unattended multi-day deployment; the rotation change alone does not bound total storage.
4. **Facility metrics:** collect synchronized, fixed-camera footage and surveyed calibration points before accepting occupancy, overlap, queues and transitions.

Research cross-checks: [FFprobe](https://ffmpeg.org/ffprobe.html) distinguishes `-count_frames` (decodes) from `-count_packets` (demuxes only); [SQLite](https://www.sqlite.org/pragma.html#pragma_synchronous) documents WAL/NORMAL's consistency versus power-loss durability tradeoff; [TensorRT performance guidance](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/best-practices.html) recommends measuring end-to-end workloads before optimizing. The repository keeps its pinned TensorRT 10.16 environment; current general guidance is not a reason to change engine/runtime versions without validation.

## Host setup notes (this workstation)

- Python 3.12 in `.venv-windows` (runtime, test and browser-test dependencies, including Playwright).
- Node.js 24 and npm 11 (official installer).
- FFmpeg/ffprobe 9.0.2 in `%LOCALAPPDATA%\Programs\FFmpeg`. Windows blocks user PATH writes here, so `scripts\a6000\env.ps1` adds that directory itself.
- WSL2 `Ubuntu-22.04` with Docker Engine as a systemd service (no Docker Desktop) and the NVIDIA Container Toolkit.
- Git LFS initialized; Git long paths enabled for the repository.

## Limits

Only `cam-01` has footage. Occupancy, zone and floor metrics and cross-camera de-duplication need surveyed camera calibration. RT-DETR's accuracy is not established. Multi-feed capacity on the A6000 and the 30-minute soak have not been run. See `README.md` and `docs/operations-guide.md`.
