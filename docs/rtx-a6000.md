# RTX A6000 workstation profile

The project runs on its target deployment, an RTX A6000 workstation, with a dedicated profile in `configs/a6000/`. It is generated from `configs/` by `scripts/a6000/configure.py` and is selected automatically by `Start-Aegis.cmd` when an RTX A6000 is detected. The upstream `configs/` (laptop, RTX 5070 Ti) are unchanged.

Validated on 2026-11-04: Dell Precision 5820, NVIDIA RTX A6000 (48 GB, sm86, driver 596.71), Windows 10 Pro for Workstations, WSL2 `Ubuntu-22.04`, Docker Engine 29.9.2 with the NVIDIA Container Toolkit 1.20.1, the pinned DeepStream 9.2 image (TensorRT 10.16).

## Start

Double-click **`Start-Aegis.cmd`** (or run it from a terminal), then open **http://127.0.0.1:8000/** and click **Start demo**. Keep the window open; **Ctrl+C** stops the server. `Start-Aegis.cmd -Dev` starts the development UI at http://127.0.0.1:7100/ instead.

Stop a server started in the background with `.venv-windows\Scripts\python.exe scripts\a6000\stop-server.py` (`--port N` for a non-default port; it stops the demo first and refuses to touch any other process on the port). A second backend on the same database refuses to start, on any port (an OS lock on `<database>.lock`). Start the server from a terminal that stays open: a backend whose console was closed keeps serving, but every `wsl.exe` it starts fails (`0xC0000142`), so readiness reports `not_ready`.

WSL shuts its VM down a minute or so after the last Windows process detaches from the distro, which also stops Docker: the dashboard then reported `not_ready` and the next **Start demo** waited for WSL to boot. The launcher therefore keeps WSL running while the server runs (a `wsl.exe ... sleep infinity # aegis-keepalive-<checkout hash>` attached to its console) and waits for Docker before starting the server (each Docker probe has a 15 s timeout, the whole wait 90 s). The keep-alive ends with the launcher (Ctrl+C, closing the window, or `stop-server.py`, which also removes one whose launcher was killed). A manual `wsl --shutdown` still stops WSL; the next Start demo then boots it again (~15 s).

Runtime state (SQLite database, evidence, capability cache) is kept in `.install\a6000\state`, outside the repository's checked-in historical databases. Set `CCTV_CONFIG_DIR` to override the profile.

## What the profile changes

| Setting | `configs/` (laptop) | `configs/a6000/` | Why (measured on the A6000, `reports/a6000/optimization-receipt.json`) |
| --- | --- | --- | --- |
| TensorRT engines | sm120 engines | sm86 engines built on the A6000 | Engines are GPU-architecture specific |
| Selected detector | TrafficCamNet (provisional smoke) | **RT-DETR, FP16 engine** (`candidate_evaluation`) | On the crowded demo clip: ~68 tracked people per frame vs ~17 for TrafficCamNet (RF-DETR: ~40) |
| RT-DETR precision | FP32, strongly typed | **FP16** | 2.4 ms vs 5.1 ms per frame; reproduces the FP32 boxes (99.4 % matched at IoU >= 0.5, mean IoU 0.994, 72.3 vs 72.5 detections per frame) |
| `cam-01` replay | once (ends at 23.7 s) | **`loop: true`** | The dashboard stays live until Stop instead of going stale at the end of the clip |
| Tracker | NvDCF perf | unchanged | `maxTargetsPerStream` 150 vs 300 gave identical tracks on this clip |

RT-DETR stays labelled *Candidate · unaccepted* everywhere: no human-reviewed accuracy evaluation exists yet (`docs/annotation-guide.md`).

Measured results with this profile:

- Paced demo, 5 minutes: 12 passes of the clip, 29-30 fps, 60-78 people in view, a flat ~225 ms backend queue, 601 contiguous history samples.
- Unpaced, the full application path (decode, detector, tracker, analytics, persistence) runs ~220 fps for one feed.
- Detector throughput in the pipeline (unpaced, decode + detector + tracker): TrafficCamNet 496 fps, RT-DETR FP32 165 fps, RF-DETR FP32 139 fps.

### Reduced analysis rate and the 12-pipeline limit

`--plan ladder --analysis-frame-interval 4` (stage D, every 4th decoded frame analysed: 7.49 fps per camera, above the 7.2 fps gate; a recorded deviation, so not acceptance-eligible):

| Feeds | Result | Analytics fps per camera (min) | Receive-to-result p95, worst camera | Backlog growth | Missing | GPU util p95 | NVDEC p95 | GPU temp max | GPU power p50 | VRAM max | Host CPU p95 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 8 | PASS | 7.49 | 448 ms | 3 ms | 0 | 39 % | 33 % | 73 °C | 118 W | 4.2 GiB | 31 % |
| 12 | PASS | 7.49 | 801 ms | 2 ms | 0 | 58 % | 48 % | 82 °C | 163 W | 6.7 GiB | 78 % |
| 16 | FAIL: 4 cameras could not start | 7.49 (the 12 that ran) | 736 ms | 1 ms | 0 | 45 % | 33 % | 78 °C | 135 W | 6.6 GiB | 40 % |

(`a6000-ladder-interval4-20261104T130140Z` for 8 and 12; `a6000-ladder-interval4-waves-20261104T165416Z` for 16.) Analysing every 4th frame cuts the per-camera cost about 3x: 8 cameras use 39 % GPU and 31 % CPU, against 99 % and 100 % at the full rate.

More than 12 camera pipelines do not run on this workstation, whatever the analysis rate:

- 16 cameras starting at once: most failed GPU allocations while loading (TensorRT `OutOfMemory` for a 30 MB request with ~4 GB of 48 GB in use, then the ONNX rebuild fallback failed the same way), and every camera waited out the 60 s first-frame deadline. Fixed in the backend: at most `replay.startup_concurrency` (default 4) cameras load at once, and a start fails as soon as the container log shows the pipeline could not reach PLAYING (`docs/decisions.md`).
- With the waves, cameras 1-12 started in about 40 s and ran normally, but cameras 13-16 failed at once with `Unable to set device in gst_nvstreammux_change_state`.
- A diagnostic with 16 decode-only containers (no detector; `--plan custom --stages A --feeds 16`) also failed: 5 decoders reported `nvv4l2decoder: Failed to allocate required memory` and the others stalled. 16 plain CUDA contexts, in one container or in 16, all succeed. So the limit is the number of DeepStream video pipelines (decoder plus CUDA device) that WSL2 grants on this GPU, not VRAM, host memory, WSL memory (24 GB still free), CPU or temperature.

So 12 cameras at an analysis interval of 4 is the measured capacity of this workstation as built (one container per camera). More would need several cameras batched into one pipeline (one process and decoder pool; a runtime change) or native Linux instead of WSL2, and each needs its own measurement. The accuracy cost of analysing every 4th frame is not measured.

Superseded and disclosed:
- `a6000-ladder-interval4-20261104T130140Z` step 16: the startup failure above, before the waves; see its `NOTE.md`.
- `a6000-ladder-20261103T230400Z`: 4+ cameras failed the old fixed 15 s startup deadline.
- `a6000-soak-20261103T230400Z`: same failure.
- `a6000-soak-20261104T002411Z` and `a6000-soak-20261104T020806Z`: each FAILED only on four t=0 history probes, taken before the first history sample existed, while every performance gate passed. The probe start condition took two fixes; see each run's `NOTE.md`.

## Rebuild, regenerate, validate

The sm86 engines are in Git LFS (`git lfs pull`). To rebuild them on an A6000 (existing engines are kept; delete one to rebuild it):

```powershell
wsl -d Ubuntu-22.04 --cd "$PWD" -e bash scripts/deepstream.sh bash /workspace/scripts/a6000/build-engines.sh
.venv-windows\Scripts\python.exe scripts\a6000\configure.py generate   # re-pins engine and config hashes
```

After any change to `configs/*.yaml` or an infer config, run `configure.py generate` and commit the result; `tests/test_a6000_profile.py` (and `configure.py check`) fail while the profile is out of date.

Fast regression check (no GPU), after `. scripts\a6000\env.ps1` so FFmpeg is on PATH: `.venv-windows\Scripts\python.exe scripts\check.py --require-artifacts` (317 Python tests with no skips, 47 frontend tests, build).

Validation on the A6000:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\a6000\validate-profiles.ps1
# isolated backend on port 8779 (the server on 8000 may keep running):
.venv-windows\Scripts\python.exe scripts\a6000\validate_overlay_recovery.py
# with the server running (Start-Aegis.cmd):
.venv-windows\Scripts\python.exe scripts\a6000\validate_browser_loop_overlay.py
```

- `validate-profiles.ps1`: each detector profile runs the full clip on the GPU (looping off): 710/710 frames, positive counts, source-time history, a real evidence snapshot and clip, a clean stop and confirmed container removal. Evidence: `reports/validation/a6000-profiles-<UTC>/`.
- `validate_browser_loop_overlay.py`: a paced run in headless Chrome for 40 s, past the end of the clip: the camera stays live, the boxes overlay is painted, the preview stays within 1 s of the pipeline (measured ≤ 0.2 s), and Stop releases the container. Evidence: `reports/validation/a6000-browser-loop-overlay-<UTC>/`; `--readme-screenshots` also copies the screenshots under `reports/ui/`.
- `validate_overlay_recovery.py` (latest: `reports/validation/overlay-recovery-20261104T032309154853Z`, 18/18, including the new independent container-absence check; the preceding run `...032139097700Z` caught an overlay regression, explained in its `failure-analysis.json`): starts an isolated backend on port 8779 with fresh local state, checks loop evidence, injects an overlay-only HTTP failure, checks recovery and epoch cursors, then exercises unpaced playback at 390 px. Evidence: `reports/validation/overlay-recovery-<UTC>/`. Repeatable runs: `reports/validation/overlay-recovery-20261103T213228598288Z/result.json` (17/17, with source hashes) and, after the follow-up review changes below, `reports/validation/overlay-recovery-20261103T215127357311Z/result.json` (17/17). The preceding validator preflight failure and its explanation are retained in `overlay-recovery-20261103T213142212839Z`; no camera pipeline started in that failed preflight.

## Independent review and improvement priorities — 2026-11-04

The local history and GitHub matched at `984f439` after fetching. The two workstation commits add looping/overlay/SQLite reuse (`4cf4070`) and the reproducible A6000 profile (`984f439`). The review checked their source changes, project-local development transcripts and committed measurements. GitHub had no issues, pull requests or workflow runs at review time.

Corrections implemented:

- Detection polling now scopes cursors and in-flight responses to the camera epoch. Failed requests time out, and boxes expire even while WebSocket snapshots remain live. Equal-position matches prefer the newest replay pass.
- Evidence mapping refuses unobserved loop boundaries instead of silently reusing an older pass. The frame-count fallback (no header count) stays a packet count: an MP4 header's `nb_frames` is itself a sample count, and decoding the whole file (`-count_frames`, 5.4 s vs 0.2 s for the demo clip) would delay the camera's start and time out on long MKV/TS recordings.
- `scripts/check.py` runs the fast checks with isolated runtime paths. GitHub Actions runs Windows/Linux checks without downloading historical LFS data. Asset checks distinguish LFS pointers from binaries and detect an individually missing A6000 engine. The first CI run exposed a test that assumed the checkout is on drive C: (GitHub's Windows runners use D:); fixed, and GitHub Actions `Checks` (`.github/workflows/checks.yml`) passes on Windows and Linux (run 41726617017 and later).

Follow-up review corrections (same day): the frame-count fallback was kept as a packet count (above); a fallback for browsers without `AbortSignal.any` was added (the overlay was otherwise silently empty there); WSL is kept running by the launcher (see *Start*).

### Second review (opencode, 2026-11-04) and what was done

Each point was checked against the code before acting:

| Finding | Verdict | Action |
| --- | --- | --- |
| A second backend on the same database (other port) runs startup recovery and releases the first one's cameras | Confirmed from source | OS lock on `<database>.lock` before migrations/recovery (`backend/app/services/instance_lock.py`); refusal, crash release and separate-database tests in `tests/test_instance_lock.py` |
| The capacity benchmark always used `configs/` | Confirmed (`load_configuration(ROOT / "configs")`, `copytree(ROOT / "configs")`) | `--config-dir` / `CCTV_CONFIG_DIR`, used for all stages and recorded; tested for both profiles |
| Frame-log rotation could truncate benchmark windows | Confirmed for the backend stage (256 MiB default; stages A-C never rotate) | Rotation and looping off in the benchmark's profile copy; a rotated log fails the step as incomplete |
| The browser fallback left one listener per request on the poll signal | Confirmed | Request signals are disposed in `finally`; one code path for every browser; listener/timer-count test |
| Evidence retention could delete a just-created record, then the API dereferenced `None` | Confirmed (`max_records: 1`) | Atomic snapshot+clip groups, group eviction, newest group kept, serialized; tests for `max_records: 1`, an oversized clip, 8 concurrent captures and a failed registration |
| Overlay freshness ignored response transit time | Confirmed | Round trip subtracted (conservative) |
| Launcher: unbounded Docker probe, raw distro parsing, start/stop port mismatch, untagged orphan cleanup | Confirmed | 15 s per-probe timeout, quoted-value parsing, `stop-server.py --port`/`BACKEND_PORT`, per-checkout keep-alive tag and a parent-PID-reuse check |
| *(found by the first A6000 ladder run)* 4+ cameras started together all failed at startup | Confirmed: the first-frame deadline was fixed at 15 s, and concurrent starts take longer (8.6 s for 1 camera, 11.7 s for 2, 16 s for 8) | New `replay.startup_timeout_seconds` (60 s); test in `tests/test_service_maker.py` |
| Packet count is a fast-path assumption | Agreed in principle | Unchanged: evidence already refuses unobserved loop boundaries; the startup cost of decoding is unchanged |
| Seek-time overlay alignment (`requestVideoFrameCallback`) | Valid | Done: boxes follow the last presented frame while playing or seeking (`DetectionOverlay.tsx`); the overlay validator caught and confirmed the fix |
| Periodic retention | Valid | Done (2026-11-04): `backend/app/services/retention.py` enforces the database limits and evidence limits at startup and every 10 minutes; see `docs/operations-guide.md`, *Database retention* |

Recommended next measurements, in order:

1. **Accuracy:** review the existing annotation package, then measure precision/recall/count error for all candidates on the same frames. More tracked boxes does not prove fewer counting errors; FP16/FP32 agreement measures numerical consistency only. Existing strict cross-pipeline disagreements remain disclosed in `reports/model-evaluation/numerical-status-20261028.json`.
2. **Capacity:** done 2026-11-04 (see *Capacity*): the A-D stage comparison passes; 8 duplicate feeds pass at the full 30 fps (GPU and CPU saturated) and 12 at every 4th frame; 13+ pipelines cannot start under WSL2 on this host. Next: batch several cameras per pipeline (or test native Linux) before planning more than 12 cameras, measure the accuracy cost of the reduced rate, and repeat with distinct real feeds.
3. **Long-running storage:** database and evidence retention are enforced (startup + every 10 minutes; age limits, then the `max_database_mib` budget). The 30-minute 4-camera soak wrote about 8 MB (mostly visible-count history), so the 2-day metrics window holds roughly 0.8 GB for 4 cameras; size `max_database_mib` for the camera count. Frame logs are bounded per epoch (256 MiB plus the previous file); old epochs' frame logs are not removed automatically.
4. **Facility metrics:** collect synchronized, fixed-camera footage and surveyed calibration points before accepting occupancy, overlap, queues and transitions.

Research cross-checks: [FFprobe](https://ffmpeg.org/ffprobe.html) distinguishes `-count_frames` (decodes) from `-count_packets` (demuxes only); [SQLite](https://www.sqlite.org/pragma.html#pragma_synchronous) documents WAL/NORMAL's consistency versus power-loss durability tradeoff; [TensorRT performance guidance](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/best-practices.html) recommends measuring end-to-end workloads before optimizing. The repository keeps its pinned TensorRT 10.16 environment; current general guidance is not a reason to change engine/runtime versions without validation.

## Host setup notes (this workstation)

- Python 3.12 in `.venv-windows` (runtime, test and browser-test dependencies, including Playwright).
- Node.js 24 and npm 11 (official installer).
- FFmpeg/ffprobe 9.0.2 in `%LOCALAPPDATA%\Programs\FFmpeg`. Windows blocks user PATH writes here, so `scripts\a6000\env.ps1` adds that directory itself.
- WSL 3.0.1 with `Ubuntu-22.04` (`systemd=true`), Docker Engine as a systemd service (no Docker Desktop) and the NVIDIA Container Toolkit. No `.wslconfig` changes; the launcher keeps WSL running instead.
- Git LFS initialized; Git long paths enabled for the repository.

## Limits

Only `cam-01` has footage. Occupancy, zone and floor metrics and cross-camera de-duplication need surveyed camera calibration. RT-DETR's accuracy is not established. Capacity figures come from duplicate copies of one clip: they measure load, not distinct-camera coverage. At 8 full-rate feeds the GPU and CPU are saturated; at every 4th frame 12 feeds pass, and no more than 12 camera pipelines start on this host under WSL2. Database and evidence retention run at startup and every 10 minutes; facility crossing totals, alerts and provenance are kept for a whole run, and `track_samples_days` has no table to act on. The 256 MiB frame-log bound applies per epoch, and old epochs' frame logs are not removed automatically. `analysis_frame_interval` raises capacity (12 cameras at 4), but its effect on counting accuracy is not measured. See `README.md` and `docs/operations-guide.md`.
